# Student usability review

Reviewed the student journey in the current source: joining, exploring, reading and saving evidence, writing an explanation, receiving feedback, and revising. The review combines a code walkthrough with a local browser playtest. It is not an observed student study.

The main friction was the transition from exploration to a supported explanation. Students could open the writing panel without knowing the criteria, and returning to an earlier answer required manually copying it. A refresh also discarded an unfinished draft.

| Student question | Issue found | Improvement |
| --- | --- | --- |
| What should I do first? | The journal said to inspect an item, although reading alone did not save it. | Added a next-step card, a direct first-evidence action, and explicit instructions to choose **Save to journal**. |
| Did I save this? | Saved state depended mainly on an icon and border color. | Evidence cards now say **Saved** or **Not saved**. |
| What will my answer be judged on? | Detailed criteria appeared after the first submission. Archive requirements were vague. | Added a pre-submission explanation checklist, with subject-appropriate reasoning guidance, and the actual archive requirements. |
| Will I lose my writing? | Drafts only lived in component state. | Drafts are saved in this browser by classroom and learner, restored on return, and removed when successfully submitted and unchanged. A save-status message indicates when a draft is not saved. |
| How do I improve my answer? | The next question was tucked into a truncated dock subtitle. There was no reuse action. | Added a full revision question and **Revise my last answer**, which preserves an existing draft and restores the prior answer's scenario. |
| Which scenario am I discussing? | Argument history did not distinguish baseline and hypothetical attempts. | Added scenario labels to each attempt and the composer. |
| Why can't I submit after citing? | Programmatic citation insertion could exceed the textarea's 1,600-character limit. | Citation insertion checks available space and explains how much room is needed. |
| How do I come back tomorrow? | Opening the same invitation always offered a new join, creating a separate learner without the earlier work. | Added an explicit **Continue as…** action that validates the saved learner with the server before opening their work. Teacher previews are excluded. |
| What if I visited a different class? | Only the most recently used classroom access was remembered. | Remember access by classroom as well as the current session, with compatibility for older saved access. |
| Why did refreshing send me to the landing page? | Joining through the original invitation removed its query parameters but kept the root path, which now serves the landing page. | Both joining and resuming leave a refreshable `/studio` URL. New invitations use that route; original root invitations remain supported. |
| Is this my journal on a shared device? | The invitation did not distinguish returning work from a new learner. | Show the saved name when available, make resuming explicit, and label the alternative **Start a new journal**. |
| Did joining fail when browser storage was blocked? | An exception while remembering access could report failure after the server had already joined the learner. | Storage failures no longer interrupt successful entry; a message explains that the tab should stay open. |
| Did my answer go through? | A lost response could lead to duplicate submissions, and the draft was cleared before feedback finished loading. | Each submission now has a receipt ID. An unchanged retry retrieves already-saved feedback; a changed answer gets a new ID. The draft is kept until feedback is available, and newer edits survive completion. |
| Where is my feedback after reconnecting? | Polling failures appeared as persistent action errors, with no distinct recovery control. | Added a reconnecting status and retry action, cleared on a successful refresh. Pending submissions reconcile with saved feedback after a refresh or reload. |
| Can I keep reading while waiting? | Reading a new location also wrote a visit, which could conflict with an in-flight answer submission. | Location reading stays available; background visit writes pause while the answer is being submitted. |
| Why is submission unavailable? | The answer limit was only explained by a server rejection. | The composer now explains the 30-answer limit and directs students to teacher review. Submission errors appear beside the draft. |
| Why can’t I read the source note? | A catalog stylesheet gave context notes a pale background while the student reader retained pale text. The phone-width browser check confirmed nearly invisible text. | Applied explicit dark-reader colors to source and revision notes, including readable links and headings. |
| Where is this quotation in its surrounding passage? | Context displayed as an undifferentiated block. | Highlight the exact validated excerpt in its context and offer **Jump to the excerpt**, with keyboard focus and scrolling. If offsets do not match the displayed source, show plain text rather than an incorrect highlight. |
| How do I make room for a citation? | A full draft disabled citation insertion but offered no direct path to editing. | Added **Return to my draft to make room**, which opens and focuses the existing draft without changing its text. |
| What actually changes in the what-if? | The student view relied on the scene to communicate changes at each place. | Added an expandable journal comparison with baseline and hypothetical descriptions, the current scenario, and direct evidence links. The comparison explicitly treats outcomes as proposals to question, and appears only in lessons that allow scenario exploration. |
| How much evidence have I saved? | The compact journal control did not expose a visible saved count. | Added a readable count badge with an accessible singular/plural label. |
| Where did I leave my writing? | The main writing action did not distinguish an unfinished draft from starting a new explanation. | The control now says **Continue your draft** whenever writing is present. |
| Why did my what-if draft come back as baseline? | Reload restored the writing but reset the selected scenario, changing the context of the next submission. | Remember the student’s scenario per classroom and learner. A changed teacher scenario takes precedence. Disable scenario switching and submission while a returning classroom is loading, while leaving writing available. |
| How can I observe the object while writing? | Opening the museum notebook hid the photograph, requiring students to remember visual details or leave the editor. | Reused the zoomable museum photograph beside the fields on larger screens, with a collapsible reference above the fields on phones. Increased notebook text and control sizes, and renamed the exit action **Close notebook** to match its destination. |

Draft storage is local to the browser; it is not cross-device synchronization. Existing submitted work remains server-backed. No grading rules were changed.

Validation: the previous full automated run passed all 101 tests, including six new submission-retry regressions. The subsequent reading-interface and scenario-comparison changes were checked in the browser rather than adding implementation-mirroring unit tests. TypeScript checking and the production build passed. The return-flow API smoke check from the prior pass verified restoration of the same learner and evidence without a duplicate profile. Retry tests cover lost responses, reloads, changed inputs, the answer limit, old history, and protection of newer pending requests.

The local browser playtest confirmed evidence saving, citation insertion, opening the explanation criteria, draft restoration after reload, draft retention after a rejected submission, and Escape returning keyboard focus to the argument control. A further browser pass at 390 × 844 verified readable source notes, excerpt highlighting, jump-to-excerpt keyboard focus, the citation capacity message for a 1,590-character draft, and direct return to the editor with the draft unchanged. The temporary test text was replaced with the original sample draft and the viewport override was reset. The pilot reported that live AI was paused, so a completed live feedback turn could not be tested; no generated reply or score was substituted. Fault injection for an interrupted in-flight network request and a broader mobile/device matrix remain untested.

The production build reports the existing large-client-bundle warning; load time on school devices remains unmeasured.

The scenario-comparison browser pass verified that the Harbor action opens its matching evidence without saving it, the current-scenario label follows the What-if switch, and **Continue your draft** opens the unchanged 267-character sample explanation. At 390 × 844, the journal count and draft control fit, and the comparison text remained readable in the scrolling journal. The viewport override was reset afterward.

The scenario-restoration pass reproduced the reset in the browser before the fix. Afterward, What-if and Baseline survived separate reloads; the restored composer showed What-if with the original 267-character draft intact. All 136 automated tests passed, including four new regressions covering both selections, changed teacher defaults, classroom/learner isolation, and malformed or blocked storage. TypeScript and the production build passed. Scenario memory is browser-local; teacher changes were covered by the storage regression rather than a live multi-browser classroom test.

The museum-notebook visual pass checked the side-by-side layout at 1280 × 900, zooming to 150% with a temporary observation intact, and the collapsed reference at 390 × 844. No test note was submitted or saved; the notebook was confirmed empty afterward and the viewport reset. TypeScript and the production build passed. These presentation changes were verified in the browser without adding unit tests.
